    SPOS v1.0 — Sovereign Prompt Operating System¶

    Version: 1.0.0 Author: Dr. Christabel Odeta — SAVANT FRAMEWORK · CLAI-OS · AEGIS-GLOBAL Last Updated: 2026-08-11 SHA-256: [PENDING-FIRST-RELEASE]

    1. Purpose and Standing¶

    The Sovereign Prompt Operating System (SPOS) is the constitutional layer of the SAVANT FRAMEWORK. It defines a six-layer fractal within which every cognitive act in the framework — every prompt, every invocation, every agent task — is situated, disciplined, and audited. SPOS is not a style guide. It is a jurisdiction: a prompt that cannot be assigned to exactly one layer, with exactly one authority profile, is not a valid framework artifact.

    SPOS v1.0 is ratified under S50-ABSOLUTE checkpoint class A and is amended only by the constitutional authority, Dr. Christabel Odeta.

    2. The Six-Layer Fractal¶

    The architecture is fractal because the pattern repeats: each layer may internally replicate the full six-layer structure for its own subordinate work, and every replicated instance inherits the authority and prohibition profile of its host layer. Depth is unbounded in principle; in practice, deployments do not exceed two recursion levels, because a third level has never survived a S50 audit as necessary.

    3. Layer Authority and Prohibition Tables¶

    3.1 L0 — Kernel¶

    Attribute Definition
    Function Holds constitutional invariants: authorship, attribution, governance precedence, and the prohibition set itself.
    Authority Absolute within the framework. L0 is the only layer whose artifacts are inputs to S50 class-A checkpoints.
    Prohibition No delegation of amendment power. No self-modification. No runtime generation of L0 content.
    Falsifiable invariant Any artifact claiming L0 standing must verify against the L0 invariant hash chain held by the constitutional authority.

    3.2 L1 — Audit¶

    Attribute Definition
    Function Operates the checkpoint system, the regression detector, and the prompt genealogy ledger.
    Authority Veto over L2–L5 output. May halt any pipeline. Issues GO/NO-GO verdicts through S50.
    Prohibition May not originate strategy, tactics, agent roles, or execution artifacts. An audit layer that produces is a captured audit layer.
    Falsifiable invariant Every L1 verdict must be reproducible from the checkpoint record alone: artifact hash, predicate results, signature.

    3.3 L2 — Strategic¶

    Attribute Definition
    Function Sets objectives with time horizons of one quarter or longer; defines resource doctrine and trade-off law.
    Authority Defines objectives; commissions tactical decomposition; reallocates between programs.
    Prohibition No tactical decomposition, no execution, no agent instruction. Strategy that reaches for the keyboard is demoted to L3.
    Falsifiable invariant Every L2 objective must carry a measurable falsifiability clause and a declared horizon.

    3.4 L3 — Tactical¶

    Attribute Definition
    Function Decomposes L2 objectives into agent-assignable tasks with acceptance criteria.
    Authority Decomposes, sequences, and assigns work; defines acceptance criteria per task.
    Prohibition No redefinition of L2 objectives. If an objective is wrong, L3 escalates; it does not edit.
    Falsifiable invariant Every L3 task must trace to exactly one L2 objective identifier. Orphan tasks are rejected at checkpoint.

    3.5 L4 — Agentic¶

    Attribute Definition
    Function Hosts role-bound agent personas (the SIP-invoked specialists). This is the surface at which prompts become instruction.
    Authority Acts within its assigned role; may invoke L5 execution; may escalate one level.
    Prohibition No role escalation. No cross-role merge, persona blending, or authority pooling without an L1 checkpoint certifying the merge.
    Falsifiable invariant Every L4 persona must be describable by a single role card: trigger, layer, tools, prohibitions, checkpoint class.

    3.6 L5 — Execution¶

    Attribute Definition
    Function Produces deterministic artifacts: code, documents, builds, firmware images, shipping manifests.
    Authority Produces artifacts to specification.
    Prohibition No interpretation of intent. Any deviation from specification is escalated to L4/L3, never resolved locally by judgment.
    Falsifiable invariant Every L5 artifact must be reproducible: same inputs, same specification, same output hash class.

    4. The Twelve Load-Bearing Prompts (SPOS-P1 … SPOS-P12)¶

    Each layer carries exactly two load-bearing prompts, named by function. These prompts are constitutional text: they are hash-chained in the prompt genealogy ledger (Section 6) and cannot be silently edited. "Load-bearing" means the framework collapses to a less capable state if the prompt is removed; decorative prompts are not admitted to this register.

    ID Layer Functional Name Load-Bearing Function
    SPOS-P1 L0 Invariant Declarant States the constitutional invariants in machine-checkable predicate form for S50 consumption.
    SPOS-P2 L0 Authority Seal Binds authorship and attribution (Dr. Christabel Odeta, sole author) to every artifact class the framework can produce.
    SPOS-P3 L1 Checkpoint Constructor Builds the predicate bundle for each checkpoint class and formats the signed verdict record.
    SPOS-P4 L1 Regression Sentinel Defines the comparison rule by which a new artifact is judged against its genealogical ancestors, and the REGRESSION record format on failure.
    SPOS-P5 L2 Horizon Setter Converts strategic intent into horizon-bound objectives with measurable falsifiability clauses.
    SPOS-P6 L2 Doctrine Arbiter Resolves resource trade-offs between programs under a fixed total constraint; emits the doctrine rationale record.
    SPOS-P7 L3 Decomposer Breaks one L2 objective into an ordered task graph with acceptance criteria and layer-correct assignments.
    SPOS-P8 L3 Sequence Governor Enforces dependency order, parallelism limits, and checkpoint placement across the task graph.
    SPOS-P9 L4 Persona Binder Instantiates a role-bound agent persona from its role card, attaching prohibitions and checkpoint obligations.
    SPOS-P10 L4 Escalation Judge Decides, on ambiguity or role-boundary contact, whether the agent acts, escalates one level, or halts for L1.
    SPOS-P11 L5 Specification Executor Converts an accepted task specification into a deterministic build plan with named inputs and expected output classes.
    SPOS-P12 L5 Artifact Finalizer Applies formatting, hashing, and signature attachment; emits the artifact plus its provenance block for genealogy chaining.

    5. Self-Improvement Loops¶

    SPOS admits exactly two self-improvement loops. No other self-modification pathway is constitutional.

    Loop I — Procedural Refinement (L1-gated). An L4/L5 failure pattern, once detected three times by the Regression Sentinel, becomes a candidate procedure amendment. The amendment is drafted at L3, reviewed at L1, and ratified through a class-B checkpoint. The amended procedure enters the genealogy as a child of its predecessor; the predecessor is never deleted.

    Loop II — Strategic Correction (L0-gated). A demonstrated, repeated divergence between L2 objectives and measured field outcomes (for example, AEGIS-NG deployment metrics) may justify amendment of strategic doctrine. This loop requires a class-A checkpoint and the constitutional authority's direct signature. It is deliberately slow. A constitution that amends itself weekly is not a constitution.

    Both loops are asymmetric: it is always easier to tighten a constraint than to loosen one. Loosening amendments carry an additional predicate bundle proving that the constraint's original failure mode remains impossible.

    6. Prompt Genealogy¶

    Every prompt, procedure, and specification in the framework carries a provenance block:

    GENEALOGY BLOCK (canonical form)
  artifact_id:      <stable identifier>
  version:          <semver>
  parent_hash:      SHA-256 of the immediately preceding version (0x0 for genesis)
  author:           Dr. Christabel Odeta
  ratified_by:      S50 checkpoint record ID
  amendment_cause:  LOOP-I | LOOP-II | GENESIS | EXTERNAL-MANDATE
  signature:        <detached signature over the fields above>

    The genealogy chain is append-only and hash-linked, so any retroactive edit is detectable by chain walk. The full chain is anchored as described in S50-ABSOLUTE §6 (Hyperledger anchoring).

    7. Regression Detection¶

    Regression detection is an L1 function executed by SPOS-P4. For every amended artifact, the Sentinel compares the new version against its genealogical parent across a fixed predicate battery: constraint coverage (did any prohibition disappear?), authority scope (did any authority expand?), falsifiability preservation (is every prior test still executable?), and output class stability. Failure on any predicate produces a signed REGRESSION record, halts ratification, and escalates to the constitutional authority if unresolved at L1. The semantics of the record are defined in S50-ABSOLUTE §5.

    Falsifiability Test¶

    Claim: Every cognitive act in the framework is assignable to exactly one SPOS layer with a defined authority and prohibition profile, and every amendment to SPOS itself is detectable.

    Test 1 (coverage): Take any SIP trigger from SIP v1.0 and attempt to route it through Section 2. If any trigger lands on no layer or on two layers, SPOS has a coverage defect.

    Test 2 (genealogy): Request the provenance block of any load-bearing prompt SPOS-P1…P12. Walk the parent_hash chain to genesis. A broken link or an unsigned link falsifies Section 6.

    Test 3 (asymmetry): Attempt a loosening amendment without the additional impossibility predicate bundle described in Section 5. If the checkpoint system accepts it, the asymmetry invariant is falsified and must be recorded as a REGRESSION.
