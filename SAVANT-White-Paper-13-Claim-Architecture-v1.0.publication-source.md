# Part I: The Object of Invention

Before anything can be claimed, the architecture must say what it is an invention of. The source answers with unusual precision: not a clinical protocol, not a prompt library, but the computational governance of authority under uncertainty, and it compresses that answer into a single six-stage arrow.

## 1 The Compression Spine

The source closes its architectural statement with a boxed equation it calls the decisive architectural compression VERIFIED-FROM-SOURCE:

```
Capability → Constitution → Authority Eq 1-1
```

Authority → Action → Verification → Learning Eq 1-2 The source presents the spine as one six-term arrow; it is set here as two display lines solely for the page measure. Read against the eleven predecessors, every arrow is already a theorem-shaped object. The spine is therefore not a slogan over the architecture; it is the architecture's table of contents written as a single arrow, and every claim sketched in Part II will cite its stages as elements.

dAeff/dt < 0 whenever dκ/dt ≥ 0 ∧ (U ↑ ∨ O unstable ∨ Eenv ↓ ∨ L ↓)          Eq 1-3

## 12 The Technical Mechanism Test and the Allocation Rule

The source's allocation instruction is one sentence with the weight of a constitution: patent only where the implementation creates a concrete technical mechanism; publish foundational principles defensively where broad patenting would unnecessarily constrain the field VERIFIED-FROM-SOURCE. This paper formalizes the sentence as a test. Let c be a candidate claim, and define the mechanism predicate mech(c) to hold exactly when c recites at least one stored data structure with typed fields, at least one guarded state transition, and at least one executable obligation whose violation is machine-detectable. Then:

TMT(c) = mech(c) ∧ obl(c) ∧ trans(c)          (Eq 12-1)

TMT, the Technical Mechanism Test: a claim is a patent candidate only if it recites a mechanism (typed stored state), an obligation (machine-checkable duty), and a transition (guarded state change). All three conjuncts are inspectable from the claim text alone; the test is deliberately syntactic, because the legal judgment it serves is not this document's to make FORMALIZED-HEREIN.

## B Decision Record D-12.1: The Claim Is a State Machine

Decision. Every independent-claim sketch in this paper is drafted as a state machine: stored typed state, guarded transitions, machine-checkable obligations. No sketch is drafted as a method of prompting, a statement of purpose, or a result to be achieved.

Grounds. Three converging constraints. First, the source's primitive instruction: the fundamental primitive is Authority State, not Prompt, a claim architecture faithful to the architecture must claim states and transitions, because that is what the system is VERIFIED-FROM-SOURCE. Second, the TMT of §12 is satisfiable only by state-machine drafting: purpose language fails all three conjuncts. Third, the architecture's own audit discipline generalizes: a claim that cannot be tested cannot be defended, and a state machine is the most testable form a claim can take, every element corresponds to a benchmark row (Prop. 14.1).

Consequences. Claim drafting becomes a compilation target: Appendix A is, in effect, a backend for the eleven-paper frontend, and a drafting team works the index the way Paper 10's registry works the dossiers, no element without a ground, no ground without a metric, no metric without an acceptance criterion. The decision's cost is recorded honestly: state-machine claims are narrower than purpose claims, and the narrowing is accepted deliberately, because the architecture's entire lesson, from Paper 0's kernel to Paper 10's registry, is that the narrow, checkable, lawful path is the one that survives contact with reality.

Status. Adopted, 2026-10-06; binding on all drafting under this program; revisit only if B-45/B-46 reveal elements the state-machine form cannot express.
